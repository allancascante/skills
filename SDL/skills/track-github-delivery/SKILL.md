# Track delivery in GitHub

Keep the local plan and test catalog while using GitHub as the shared coordination record. An assignment, comment, local commit, or passing PR alone is not proof of exclusive ownership or task completion.

## Agree on tracking and permissions

1. Inspect project instructions, the document map, local plan, repository/remotes, existing issues/PRs, and coding/integration policy. Ask which ticketing system the team uses; recommend GitHub Issues for GitHub-hosted projects, with GitHub Projects optional. Offer existing tooling or local-only tracking as alternatives. Do not enable GitHub tracking or create remote items without confirmation. If another system is selected, record it and its equivalent ownership/status protocol; do not silently create GitHub duplicates.
2. Confirm the target `owner/repo`, remote, integration branch (`main` unless the project chooses another), issue granularity, labels or Project status mapping, and local tracker path. Confirm permissions separately for reading remote data, issue/comment/assignment/status changes, branch creation, commits, pushes, PR creation, and merging. A standing policy may authorize specific operations; selecting this skill does not. Prefer the authenticated `gh` CLI when available, otherwise supported GitHub tools. Missing authentication, permissions, or connectivity is a visible blocker, not permission to fall back to uncoordinated implementation.
3. Agree that the approved local contract/plan owns scope, requirements, dependencies, and acceptance criteria; GitHub owns live claims, ownership, blockers, and execution status when enabled. The local tracker mirrors those fields with issue/PR links and a last-synchronized time. Ask before resolving substantive scope conflicts; never overwrite a newer remote claim from a stale local file.
4. For multiple agents, confirm one claim coordinator (a human or one designated agent session) that serializes ownership grants in GitHub issue comments. Record the coordinator identity and handoff policy. Ordinary issue edits, labels, and assignees are not an atomic lock; checking and then assigning cannot guarantee exclusivity. Without an agreed serialized grant mechanism, stop concurrent task starts and ask the owner to assign work. Do not describe best-effort rechecking as a lock.

## Publish or reconcile the plan

1. Resolve the local tracker through the document map. Inspect existing open and closed issues, comments, linked PRs, and relevant commits before creating anything; paginate results and do not assume the first page is complete. Match stable local task IDs and phase IDs, not titles alone. If a create request times out, check for the created item before retrying.
2. Reuse an existing canonical issue per task where possible. If duplicates or conflicting records exist, ask which to retain; do not close, delete, or rewrite someone else's work without authorization. Only the agreed coordinator publishes new task issues during concurrent planning, so two agents do not both create the same task.
3. Give each task issue its local task/phase ID, approved scope and exclusions, requirement/scenario IDs, dependencies as issue links, acceptance criteria, required checks, and links to the plan/catalog at an available repository revision. Mark unpublished local artifacts as pending publication rather than inventing working GitHub links. Do not upload secrets, private logs, or documents to an unapproved repository.
4. Add the canonical issue URL to each local task. Record GitHub status, owner/agent-session claim, branch, PR URL, synchronization time, blockers, and remaining work as they become known. Preserve dependency and scenario traceability in both directions. Use fully qualified `owner/repo#number` references when repository context could be ambiguous.

## Refresh, select, and claim before coding

1. At session start and before every new task or resumed task, inspect worktree/branch status. When authorized, fetch the agreed remote and inspect the latest integration branch's tracker and relevant commits, plus current issues, claim/release comments, dependencies, and open PRs. Fast-forward a clean local base when safe and permitted; never blindly pull into a dirty or shared worktree, reset user work, or switch another agent's branch. Use a separate task branch and isolated worktree/clone for each active agent. Inspect linked commits and PRs for existing implementation before starting again.
2. Select only work whose prerequisites and approvals are satisfied, which is not blocked, DONE, actively claimed, or already awaiting review/integration. Dependencies are satisfied by the project's completion evidence, not merely a closed issue. Check overlapping file/state ownership with other active tasks. A stale local TODO or absent assignee does not make work available.
3. Post an authorized claim request on the issue with task ID, unique non-secret agent/session ID, accountable GitHub account, proposed branch, baseline revision, UTC time, and intended scope. Distinguish sessions even when they share one GitHub account. Do not start implementation on a request alone.
4. The designated coordinator processes requests serially, rereads the issue/dependencies/PRs, and grants at most one active claim. Record a unique claim ID, the selected session/account, branch, grant time, and the request comment link in a grant comment; set the agreed DOING status and assignee where supported. Other requests wait or select another eligible task. Do not remove other owners to make a task look available. If writes partially fail, report and reconcile before granting further work.
5. Before coding, reread the issue and confirm the current unreleased grant belongs to this session and no conflicting grant, blocker, or overlapping work exists. Record the grant URL/ID and DOING state locally. A conflict, unclear coordinator handoff, or uncertain remote state requires pausing and owner/coordinator resolution; do not resolve it with last-writer-wins updates. Local tracker commits are audit history, not the claim mechanism, and require the normal commit authorization.
6. On resume and before publishing changes, recheck the grant and remote updates. Report progress, evidence, and blockers on the issue and mirror them locally. Retain the claim while blocked unless explicitly released. A claim does not expire merely because its owner is quiet: the coordinator must confirm a release or owner-approved reassignment and record the old/new claims and existing work. For a handoff, include branch/commit/PR links, checks, remaining work, and conflicting surfaces. Never silently steal an abandoned-looking task.

## Implement, review, and integrate through a PR

1. Use `implement-tested-slice` under the active claim and approved task policy. Put intended code, tests, related documentation, and local tracker updates on the task branch. Include task/issue references in commits under the project's conventions. Report a synchronization failure in both available records and stop dependent handoffs until reconciled; do not claim remote updates succeeded.
2. Before pushing, refresh remote state and confirm ownership, base branch, and task scope again. Follow the approved merge/rebase policy without destructive resets or unauthorized history rewrites. If the base changed, run affected required checks against the updated candidate; do not carry old evidence forward as if it tested new code.
3. When authorized, push the task branch and create or update one canonical PR targeting the agreed integration branch, never pushing task implementation directly to `main`. Search for an existing PR before creating one or retrying an ambiguous request. Include issue and local task links, scope, scenario IDs, actual validation/evidence, remaining gates, and blockers. Use a non-closing issue reference such as `Refs owner/repo#number` while post-integration gates remain; avoid auto-close keywords that would imply DONE at merge.
4. Keep issue and local status DOING/PARTIAL (or the approved review state) while review, required CI, branch protections, approvals, or integration remain pending. A draft/open PR is not DONE. Address review feedback and conflicts, rerun affected checks after changes, and obtain required approvals. Do not bypass protections, self-approve on behalf of reviewers, or merge without permission.
5. Use `integrate-and-report` to verify the candidate and, when authorized, merge the approved PR into the agreed integration branch. Confirm the actual merged state and resulting revision from GitHub; a successful push, merge request, or queued merge is not a completed merge. Refresh safely and run required post-integration checks against that revision. If permissions or environments are missing, report the pending gate rather than claiming completion.
6. Only after required review, integration, and post-integration gates pass, record the PR, integrated revision, actual checks, and evidence remotely and locally; mark DONE and close the issue when authorized. If an issue closed automatically or prematurely, flag the mismatch and reopen when authorized; never infer completion from closure alone. Keep failed integration or validation BLOCKED/PARTIAL with remaining actions visible.
7. Publish final local evidence/status changes through an authorized follow-up PR when they could only be known after the implementation PR merged. Until publication, record the pending documentation sync on the issue and in the local report; do not claim the default-branch tracker is current. Confirm both records agree before reporting full synchronization. A closed-unmerged PR releases no claim by itself: record whether work is retained, handed off, or explicitly released before selecting more work.

## Done when

The approved local plan links to canonical GitHub tasks; active work has an unambiguous coordinator-granted owner; issue and local status/evidence agree or their synchronization blocker is explicit; and completed work is linked to a reviewed, merged PR with required post-integration evidence. No remote operation or exclusivity guarantee is implied merely by documenting this workflow.
