# Clarify a supplied specification

Turn a detailed supplied spec into a reviewed input for contract finalization. This is an analysis and interview workflow, not permission to design, implement, or approve requirements on the user's behalf.

Invoke this skill again for each newly supplied phase, release, or substantial specification revision. Prior approval does not automatically approve new requirements. Reuse earlier confirmed answers where still applicable, but explicitly review changed assumptions and compatibility.

## Procedure

1. Ask for the specification as a file, attachment, or pasted content if it is not already provided. Identify its version, scope, related sources, and the decision owner. Read the full accessible spec, including referenced material needed to understand it; disclose missing or unreadable sources and request them rather than pretending the review is complete. Keep private material within authorized tools.
2. Resolve destinations through the agreed document map or existing project links. If absent, ask whether to retain existing paths, use `docs/specs/SPECIFICATION.md` and `docs/specs/SPECIFICATION-CLARIFICATIONS.md`, or choose custom locations; use `organize-project-docs` if available. Confirm where to retain the supplied original and whether the user wants a separate working draft or edits to an existing draft. Preserve original meaning and provenance; do not overwrite an accepted spec.
   For a new phase, identify the prior accepted contract, implementation baseline/revision, known limitations, and prior clarification records. Offer separate paths such as `docs/specs/PHASE2-SPECIFICATION.md` and `docs/specs/PHASE2-SPECIFICATION-CLARIFICATIONS.md`, incrementing the phase number as needed. Compare new requirements against prior guarantees and actual evidence; retain earlier records and qualify question IDs by phase/register so references remain unambiguous. Ask about conflicts or compatibility changes instead of silently reinterpreting prior answers.
3. Inventory the requirements and supplied scenarios, retaining existing IDs and section references. Review goals/non-goals, actors, workflows, interfaces, state/data, errors, permissions, compatibility, operational constraints, measurable nonfunctional requirements, and acceptance criteria where applicable. Distinguish explicit requirements, observations from an existing system, assumptions, contradictions, and unknowns. Do not ask the user to repeat answers already present.
4. Build a clarification register using the [template](./assets/clarification-register.md). Give each unknown a stable ID such as `Q-001`, source section/requirement, impact, priority, and blocking stage. For each, state the precise question, why it matters, and options/tradeoffs where useful. Label recommendations as proposals, not answers. Prioritize scope, safety, compatibility, conflicting requirements, and decisions that prevent further analysis.
5. Ask focused questions in small related batches using a structured question tool when available; otherwise ask in chat and wait. Include source context and enough information for an informed answer. Offer "undecided" or deferred investigation where appropriate. Do not assume a recommended default was approved if the user declines, skips, or gives an ambiguous response.
6. After each batch, persist the actual responses in the agreed register with question IDs, respondent and actual response date/reference when known, answer text or a faithful labeled summary, rationale if supplied, and affected requirements. Separate the user's response from the agent's interpretation and proposed spec wording. Clarify contradictions and uncertainty; do not fabricate rationale or approval.
7. Propose exact requirement changes based on answers. Obtain confirmation when interpretation changes behavior, scope, or constraints, then update the authorized draft or record proposed amendments if the source cannot be edited. Link each amendment to the question and affected sections; preserve prior responses and mark superseded decisions explicitly rather than erasing history. Keep architecture decisions destined for ADRs distinguishable from requirement clarifications.
8. Recheck the whole spec and register after each substantive change. Ask follow-up questions only for remaining or newly introduced gaps. Keep unanswered questions open, deferred with an owner/next action, or blocked; do not mark a question resolved merely because it was asked. If the user pauses, save a resumable state and stop interviewing.
9. Present a final review: source/version reviewed, confirmed requirements and changes, answered questions, open/deferred items and blocking stages, and recommended next action. Ask the owner to confirm the consolidated interpretation and any acceptance of deferred scope. Unresolved blockers prevent the affected stage, not necessarily every independent activity. Do not claim final approval if it has not been given.
10. Hand the reviewed spec and clarification register to `define-project-contract` for contract finalization, then to architecture and delivery planning as appropriate. If those skills are unavailable, provide the same explicit handoff without assuming automatic skill invocation. Update agreed document links with `maintain-project-docs` or direct equivalent checks.
    For a next-phase spec, include the prior-baseline comparison and unresolved compatibility questions in the handoff to `evolve-project-phase` when available.

## Done when

The supplied spec has been reviewed, actual responses and their requirement impacts are durably recorded, unresolved items and blockers are explicit, and the owner has confirmed the interpretation or the pending confirmation is clearly reported. No code, implementation status, or acceptance evidence is implied.
